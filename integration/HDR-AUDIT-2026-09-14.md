# Custom channel HDR audit

## Expanded actual-quality audit (supersedes HDR-only run)

The user requested full technical records for future measured-quality sorting.
Current worker: `venom-quality-audit-v3.service` on CT102, transient one-pass job,
12-hour runtime cap; resume script `venom-hdr-audit.py` with helper
`venom-quality-probe.py`. Report: `/data/config/iptv-venom/channel-quality-audit.json`.
Schema 3. The earlier HDR-only report remains preserved, but does not satisfy
the expanded audit. Normal/HD duplicates are sampled once per gateway channel ID.

Each five-second requested broadcast sample records decoded geometry/pixel format,
frame cadence, interlacing, codec/profile/level, aspect ratios, per-component bit
depth from FFmpeg pixel descriptors, chroma subsampling, colour primaries/transfer/
matrix/range/chroma location, audio codec/profile/channels/layout/rate/language,
reported bitrates, container and stream count. Observed video cadence and encoded
video packet-size bitrate estimate are recorded when timestamps/sizes suffice.
The estimate is not transport/network bitrate or a long-term average.

Numeric HDR/Dolby Vision side-data fields are retained when exposed (mastering,
light levels, profile, base/enhancement-layer/RPU flags). Absence is not proof that
a feature never exists. Up to 35 seconds wall time per probe; raw URLs, raw stderr,
arbitrary tags and SEI text are not saved. Decoded-frame variants are retained
separately from stream-header values. Missing metadata is null/unknown, not guessed.
Broadcast quality may change by program; this is a timestamped sample, not proof
of native camera/master resolution or a guarantee against upscaling.

The scan does not reorder categories yet. Existing label-first order remains
until measured records are reviewed. Five metadata regression tests passed and
live samples verified 1080p/25fps/H.264/8-bit output from an 8K-labelled feed.

The original HDR-only audit details follow for history.

User requested actual HDR testing, not marketing labels. One-pass audit of all
697 unique published custom channels started on media CT102. It deduplicates
normal/HD lists, prioritizes labelled high-quality feeds, shares the production
checker lock and waits for idle capacity. No categories, favourites, names or
playback configurations are modified.

`venom-hdr-audit.py` reuses fresh successful decoder measurements with explicit
HDR/SDR metadata. Remaining channels get a bounded 22-second, three-decoded-frame
probe through the existing gateway. HDR means PQ (`smpte2084`) or HLG
(`arib-std-b67`) transfer signalling. Missing transfer is unknown, not SDR;
10-bit or 8K alone is not confirmation. Results describe the sampled broadcast,
not every program a channel might show later.

Initial records: 19 confirmed SDR, zero confirmed HDR, 655 working but unknown
transfer and 23 stale/failed. The latter two groups are rechecked by this audit.
The classifier/parser has the existing nine checker regression tests.

Progress is persisted after each channel at:
`/data/config/iptv-venom/hdr-audit-report.json` (private; names/measurements only).
Fields: state, counts, pending, per-channel source/time/classification/geometry.
Safe journal records identify channel and classification, never stream URLs.
Current transient service: `venom-hdr-audit-resume.service`, maximum runtime 8h.
It terminates after a single complete pass, including unknown/inconclusive results.
It does not retry unknown feeds indefinitely or auto-restart after a reboot.
Resume by running the script again; results younger than seven days are retained.
Gateway authentication is renewed during long passes.

Inspect `systemctl status venom-hdr-audit-resume.service` and the JSON summary.
A completed pass with unknown results does not prove no HDR exists.
